<objective>
Completar a fatia vertical do painel adicionando as três rotas de AÇÃO ao MESMO `review-server.js` do Plano 04-04 (que já renderiza os formulários apontando para estas rotas): `POST /review/:productId/approve`, `POST /review/:productId/reject` (ambas acionadas pelos formulários HTML já existentes) e `POST /review/:productId/write` (endpoint machine-only, sem botão na UI — SC#3 explicitamente pede que a proteção funcione mesmo pulando a interface).

Decisão de design que fecha o Pitfall 2 do `04-RESEARCH.md` por construção, não por validação adicional: o corpo do POST de aprovação carrega apenas `removedIds` (os ids que o operador clicou "Remover" nesta sessão de curadoria) — NUNCA um campo "ids aprovados" direto. O servidor SEMPRE recomputa o conjunto final via `computeDiff`/`recomputeAfterRemoval` (Plano 04-02) a partir desses `removedIds`; não existe nenhum campo no payload que, se falsificado, poderia inserir um id que o motor não elegeria — `removedIds` só pode ENCOLHER o pool. Isso é estruturalmente mais forte que "validar que o conjunto submetido é subconjunto do calculado" (a alternativa que o RESEARCH considerou): aqui não há nada para validar, porque não há campo para injetar.

Após este plano, um operador consegue completar o ciclo inteiro: ver a fila → ver o diff → remover um item (recarregando a página com `?removedIds=`) → aprovar ou rejeitar → e qualquer tentativa de pular direto para "escrever" sem aprovação é recusada pelo backend. Inclui um checkpoint humano final contra o servidor real (não só testes automatizados) para validar visualmente o contrato do `04-UI-SPEC.md` e confirmar SC#3 ao vivo.

Purpose: fecha APRV-02/03/04 — sem este plano, o painel só exibe, nunca decide nem impede escrita indevida.
Output: `review-server.js` com as 3 rotas POST + `review-server.test.js` estendido cobrindo SC#2/3/4 + checkpoint humano.
</objective>

## Phase Goal

Antes de qualquer escrita real na loja, toda mudança de recomendação calculada é apresentada num painel web como um diff "antes vs. depois" revisável, e nenhuma gravação acontece sem aprovação humana explícita — regra aplicada no backend, não só na interface. O mesmo fluxo também suporta simulação completa (dry-run) sem tocar a loja.

Contrato de corpo das rotas POST (novo, definido por este plano — nunca aceita um campo "approvedIds"/"ids aprovados" direto):
```
POST /review/:productId/approve
  Content-Type: application/x-www-form-urlencoded (formulário HTML real) OU application/json (testes/futuro)
  Body: removedIds=<id1>,<id2>  (form)  OU  { "removedIds": ["id1","id2"] }  (json)  — ambos opcionais, default []
  -> 303 Location: /review   (sucesso)
  -> 404 (productId não existe no catálogo) | 400 (corpo malformado) | 413 (corpo grande demais) | 405 (método != POST)

POST /review/:productId/reject
  Body: ignorado (drenado, não parseado)
  -> 303 Location: /review
  -> 404 | 405

POST /review/:productId/write?dryRun=true|false   (default: DRY_RUN_MODE do servidor, ver Plano 04-04)
  Body: ignorado
  -> 200 JSON { productId, approvedIds, dryRun, written: false, reason }
  -> 409 JSON { error } quando ApprovalRequiredError (sem decisão 'approved' para productId+runId atual)
  -> 405 (método != POST)
```

| Boundary | Description |
|----------|-------------|
| `POST /review/:productId/write` sem passar pela UI → `executeApprovedWrite` | É EXATAMENTE o caminho que SC#3 pede para ser testado — precisa recusar independentemente de como foi chamado |
