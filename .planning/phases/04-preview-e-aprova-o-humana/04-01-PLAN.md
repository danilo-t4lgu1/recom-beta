<objective>
Estender a camada de persistência (`schema.sql` + `catalog-store.js`) com a infraestrutura de dados que a Fase 4 precisa para existir: uma tabela `approval_queue` nova que grava o registro de aprovação/rejeição por produto (D-25 — sempre o CONJUNTO EXATO de ids aprovados, nunca um booleano), e duas funções de leitura que faltavam completamente no módulo — `getLatestSuccessfulRunId()` (nenhuma função hoje expõe o run_id resolvido, só `getLatestSnapshotProducts()` o usa internamente) e `getBaselineForRun({runId})` (a tabela `recommendation_baseline` existe e é escrita desde a Fase 2, mas NENHUMA função de leitura foi criada até agora — confirmado por busca no código-fonte).

Correção necessária em relação ao DDL de exemplo do `04-RESEARCH.md`/`04-PATTERNS.md`: o exemplo de `approval_queue` ali usa `id INTEGER PRIMARY KEY AUTOINCREMENT` com apenas um `CREATE INDEX` (não-único) em `(product_id, run_id)` — isso NÃO habilita `ON CONFLICT(product_id, run_id) DO UPDATE`, porque o SQLite exige que o alvo do `ON CONFLICT` corresponda a uma constraint UNIQUE ou PK real, e `better-sqlite3` lança erro de preparo (`ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint`) nesse caso. Este plano corrige isso adicionando `UNIQUE(product_id, run_id)` à tabela (mantendo `id` como PK autoincrement para identidade de linha), preservando literalmente todas as outras colunas do exemplo — e permitindo o upsert-por-decisão recomendado no Open Question #2 do `04-RESEARCH.md` (seguir o padrão de `recommendation_baseline`).

Nota de estado real (2026-07-16, mais recente que `04-CONTEXT.md`/`04-RESEARCH.md` de 07-14/07-16): o `data/catalog.db` real hoje tem 354/675 produtos com `fabricTagCanonical` preenchido (a planilha JÁ foi importada desde que o contexto foi coletado), mas o run mais recente (run_id=5, executado 2026-07-15 como categoria única "Vestidos") tem `product_group_canonical` NULL para os 675 produtos — o motor (`recommendForProduct`) trata grupo-fonte nulo como fail-closed (T-03.1-02) e retorna `[]` para todo produto. Isso significa que, contra o banco real de hoje, `recommendForProduct` ainda devolve lista vazia para qualquer produto — não porque a tag de tecido está ausente (D-16, premissa antiga), mas porque nenhum run recente resolveu `product_group_canonical`. O comportamento funcional esperado (fila majoritariamente vazia) permanece válido; a causa raiz mudou. Isto não é escopo de correção deste plano (não é um bug de persistência — a Fase 4 lê o que a ingestão grava) — apenas contexto para não confundir execução futura.

Purpose: sem esta camada, não existe onde persistir uma decisão de aprovação (D-25) nem como ler o "antes" (baseline) de forma programática — as Fases 4-02 a 4-05 dependem desta base.
Output: `schema.sql` com `approval_queue` + `catalog-store.js` com 5 funções novas exportadas + `catalog-store.test.js` estendido cobrindo o round-trip completo.
</objective>

DDL corrigido de `approval_queue` (adiciona `UNIQUE(product_id, run_id)` em relação ao exemplo do RESEARCH/PATTERNS — ver `<objective>` para a justificativa técnica):

```sql
CREATE TABLE IF NOT EXISTS approval_queue (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  product_id TEXT NOT NULL REFERENCES products(id),
  run_id INTEGER NOT NULL REFERENCES ingestion_runs(id),
  status TEXT NOT NULL DEFAULT 'pending', -- pending | approved | rejected
  approved_recommendation_ids TEXT,       -- JSON array de productId, NULL se rejected/pending
  decided_at TEXT,
  created_at TEXT NOT NULL,
  UNIQUE(product_id, run_id)
);
```

Esta é uma tabela NOVA (não uma coluna nova em tabela existente) — `CREATE TABLE IF NOT EXISTS` sozinho já basta na abertura do módulo; NÃO é necessário nenhum `PRAGMA table_info`/`ALTER TABLE` (esse padrão de migração idempotente do Pitfall 2 da Fase 03.1 só se aplica a colunas novas em tabela JÁ existente, que não é o caso aqui).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Payload de aprovação (ids, status) → escrita SQL em `approval_queue` | `productId`/ids aprovados chegam eventualmente de uma requisição HTTP (Plano 04-05); nunca podem ser concatenados em SQL |
