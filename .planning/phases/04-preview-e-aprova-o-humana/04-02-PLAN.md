<objective>
Construir a camada de domínio pura que decide O QUE entra na fila de revisão (D-22/D-23) e COMO um produto individual é comparado antes/depois (D-19 a D-21), como fatia vertical testável isoladamente com fixtures — sem nenhum I/O, sem servidor HTTP, sem SQLite. `review-queue.js` responde "quais produtos mudaram?"; `diff.js` responde "o que exatamente mudou neste produto, e o que acontece se eu remover um item?".

A descoberta mais importante do `04-RESEARCH.md` (verificada por leitura direta de `recommendation-engine.js`, não suposição) governa este plano: `composeGroupQuota` tem a cota 4+4 (`GROUP_QUOTA_PER_SIDE`) FIXA independente do `maxRecommendations`/`cap` recebido — chamar o motor com um `maxRecommendations` maior NUNCA revela um "9º candidato" para produtos de Partes de Cima/Baixo (Pitfall 1). Por isso `recomputeAfterRemoval` (D-20) funciona filtrando o CATÁLOGO de entrada (removendo os ids removidos do array `catalogProducts` antes de chamar `recommendForProduct` de novo) — nunca tentando "pedir mais" do motor. Esta é a única abordagem que funciona corretamente para os 3 grupos de produto (Look Inteiro, Partes de Cima, Partes de Baixo) sem tocar `recommendation-engine.js`.

Purpose: sem esta camada, o Plano 04-04 (rotas HTTP) não tem lógica de negócio para compor — teria que reimplementar comparação de conjuntos e recomputação inline no handler HTTP, exatamente o anti-padrão que o `04-RESEARCH.md` adverte contra ("Don't Hand-Roll").
Output: `src/review/review-queue.js` + `src/review/diff.js`, cada um com seu arquivo de teste, cobrindo D-19 a D-23 com fixtures in-file (mesmo padrão de `recommendation-engine.test.js` — nunca lê `data/catalog.db`).
</objective>

## Phase Goal

Antes de qualquer escrita real na loja, toda mudança de recomendação calculada é apresentada num painel web como um diff "antes vs. depois" revisável, e nenhuma gravação acontece sem aprovação humana explícita — regra aplicada no backend, não só na interface. O mesmo fluxo também suporta simulação completa (dry-run) sem tocar a loja.

// D-20 (opção b do CONTEXT.md, confirmada única viável pelo RESEARCH — Pitfall 1): filtra
// removedIds do catálogo de ENTRADA e chama recommendForProduct de novo. Nunca duplica
// composeGroupQuota/buildSortedPool/cascata D-13 — só filtra o array antes de delegar.
export function recomputeAfterRemoval(
  productId: string, catalogProducts: CatalogProductEntry[], removedIds: (string|number)[]
): Recommendation[] // mesmo shape Recommendation de recommendation-engine.js (D-18)

// beforeIds: ids do baseline (0 ou 1 item hoje, herança do campo legado). removedIds (default []):
// ids que o operador clicou "Remover" nesta sessão de curadoria (D-19) — SEMPRE re-derivado pelo

// cliente (isso é o que torna a Fase 4 imune ao Pitfall 2 do RESEARCH: não há campo de "ids
// aprovados" para falsificar, só um filtro de exclusão que só pode ENCOLHER o pool elegível).
export function computeDiff(
  productId: string, catalogProducts: CatalogProductEntry[], beforeIds: (string|number)[],
  options?: { removedIds?: (string|number)[] }
): {
  productId: string,
  beforeIds: string[],
  afterIds: string[],              // conjunto final CURADO (pós-remoção+backfill) — é o que se aprova
  engineComputedIds: string[],     // saída do motor ANTES de qualquer remoção — auditoria/debug
  items: Array<{ productId: string, status: 'added'|'removed'|'kept', recommendation: Recommendation|null }>
}
