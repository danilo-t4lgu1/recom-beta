<objective>
Construir o motor de recomendação determinístico (RULE-01/RULE-02) como fatia vertical completa sobre fixtures: uma função pura `recommendForProduct` que recebe um `productId` + o array de produtos do snapshot (D-17) e devolve até 8 recomendações como objetos ricos (D-18), aplicando elegibilidade estrita — mesma cor, mesmo tecido canônico obrigatório para fonte E candidatos (D-15, sem nenhum fallback por cor+estoque, D-16), grade de estoque disponível obrigatória — e a cascata de desempate D-13 (estoque total → distribuição entre grades → tamanhos centrais; sem conceito de "Grupo", D-14).

Como o catálogo real tem hoje 0/645 produtos com `fabric_tag_canonical` preenchido (planilha pendente, D-16), toda a validação funcional deste plano usa fixtures in-file com tags de tecido preenchidas manualmente — nunca o dump real de `data/catalog.db`.

Purpose: este é o coração da Fase 3 — sem ele não existe o que a Fase 4 aprovar nem a Fase 5 gravar. A forma dos objetos ricos definida aqui (D-18) vira a interface de dados consumida pela Fase 4.
Output: `src/recommendation/recommendation-engine.js` + `recommendation-engine.test.js`, todos os comportamentos verdes em vitest.
</objective>

## Phase Goal

Dado um snapshot normalizado do catálogo, o sistema calcula automaticamente até 8 produtos recomendados por produto, aplicando simultaneamente mesma cor, mesmo tipo de tecido (padronizado) e estoque disponível obrigatório — de forma 100% determinística, sem IA/ML, auditável e testável isoladamente.

Shape de entrada do motor — `CatalogProductEntry` (contrato entre este plano e o plano 03-02, que materializa este shape a partir do SQLite; fixtures dos testes produzem exatamente este shape):

```javascript
// Um item do array `catalogProducts` passado ao motor:
{
  productId: string,               // id Nuvemshop como string
  name: string|null,
  colorValue: string|null,         // cor representativa do produto (origem: variants, ver IN-03)
  fabricTagCanonical: string|null, // NULL => produto fora do motor (D-15)
  hasAvailableGrade: boolean,      // resultado D-04 persistido na ingestão (>= 3 tamanhos com estoque)
  variants: [                      // ordem determinística (a mesma da leitura do snapshot)
    { variantId: string, sizeValue: string|null, stockTotal: number }
  ]
}
```

Shape de saída — `Recommendation` (D-18, interface de dados que a Fase 4 vai consumir):

```javascript
{
  productId: string,
  colorValue: string,              // valor usado no match de cor
  fabricTagCanonical: string,      // valor usado no match de tecido
  stockTotal: number,              // soma de variants[].stockTotal — número do nível 1 da cascata D-13
  sizesWithStock: number,          // contagem de variantes com stockTotal > 0 — número do nível 2
  centralSizesStock: number,       // soma de stockTotal nos tamanhos centrais — número do nível 3
  stockBySize: [                   // distribuição por grade (D-18)
    { sizeValue: string|null, stock: number }
  ]
}
```

Padrões existentes a replicar (já lidos em 03-PATTERNS.md): módulo de domínio puro com funções nomeadas e JSDoc (`stock-availability.js`), constantes de regra de negócio nomeadas (`MIN_SIZES_IN_STOCK = 3` em `ingest-catalog.js`), entrada malformada nunca lança — retorna valor seguro, helpers privados com normalização `.trim().toLowerCase()` (`findAttributeIndex`).
