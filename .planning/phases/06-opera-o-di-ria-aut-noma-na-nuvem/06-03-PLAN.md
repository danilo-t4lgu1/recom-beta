<objective>
Adicionar cache TTL de 24h (D-50) ao Script do storefront (`storefront-script/main.js`), usando `sessionStorage` nativo do navegador com funções puras testáveis por injeção de dependência (sem jsdom) — fechando FRNT-02/SC#4 (zero fetch em cache hit dentro da mesma sessão).

Purpose: o backend (`api/recommendations/[productId].js`, Vercel) chama a API da Nuvemshop AO VIVO a cada requisição — sem cache client-side, cada visualização de página repetida do mesmo produto na mesma sessão gera uma chamada de rede desnecessária. A confirmação final de "zero fetch em cache hit" é uma verificação comportamental manual (D-51), não coberta pelo `<verify><automated>` desta fase — o teste automatizado desta fase prova o comportamento das funções puras de cache, não a ausência de chamada de rede no navegador real.
Output: `main.js` com cache TTL adicionado (additive, sem restruturar o arquivo); `main.test.js` (primeiro teste automatizado deste script).
</objective>

  <behavior>
    - `getCachedRecommendation(storage, productId, now)`: retorna os dados gravados quando `now` está dentro de 24h do `cachedAt` registrado por `setCachedRecommendation` (cache hit); retorna `null` quando `now - cachedAt > 24h` (cache expirado); retorna `null` quando não há nenhuma entrada para o `productId` (storage vazio/chave ausente); retorna `null` (nunca lança) quando o valor gravado é um JSON inválido/corrompido; uma chave gravada para um `productId` nunca é retornada para um `productId` diferente (isolamento por chave).
    - `setCachedRecommendation(storage, productId, data, now)`: nunca lança quando `storage.setItem` lança uma exceção (simula Safari modo privado/quota excedida) — degrada graciosamente, mesma disciplina de `fetchRecommendation().catch()` já existente no arquivo.
    - `init()`: quando há cache hit para o `productId` atual, renderiza a partir do cache e retorna SEM chamar `fetchRecommendation` (zero fetch, SC#4); quando há cache miss, chama `fetchRecommendation` como hoje e grava o resultado no cache dentro do `.then()`, antes ou junto da renderização.
  </behavior>
  <action>
    Em `main.js`, dentro da mesma IIFE existente (não restruturar o arquivo, não converter para módulo ES — o arquivo continua sendo injetado como `<script>` clássico no navegador real via Partners Portal), adicionar logo após a declaração de `ANCHOR_AFTER_SELECTOR`: `var CACHE_TTL_MS = 24 * 60 * 60 * 1000;` e `var CACHE_KEY_PREFIX = 'recomendados_cache_';`.

    Adicionar duas novas funções (próximas a `fetchRecommendation`, mesmo estilo `var`/`function` do resto do arquivo): `getCachedRecommendation(storage, productId, now)` — lê `storage.getItem(CACHE_KEY_PREFIX + productId)`, retorna `null` se ausente; faz `JSON.parse` dentro de um `try/catch` que retorna `null` em qualquer exceção (JSON inválido); se `now - parsed.cachedAt > CACHE_TTL_MS`, retorna `null`; senão retorna `parsed.data`. `setCachedRecommendation(storage, productId, data, now)` — dentro de um `try/catch` que não faz nada no `catch` (comentário explicando degradação graciosa), chama `storage.setItem(CACHE_KEY_PREFIX + productId, JSON.stringify({ data: data, cachedAt: now }))`. As duas funções recebem `storage`/`now` como parâmetro e NUNCA leem `window.sessionStorage`/`Date.now()` diretamente no próprio corpo (dependency-injection — mesma disciplina de testabilidade já usada em `approval-gate.js`/`CATALOG_DB_DIR` do backend, Pattern 4 do 06-RESEARCH.md).

    Modificar `init()`: logo após obter `productId` (e confirmar que não é `null`), chamar `var cached = getCachedRecommendation(window.sessionStorage, productId, Date.now());`. Se `cached` for truthy, renderizar via `renderRecommendationBlock(cached.recommendedProduct)` quando `cached.recommendedProductId && cached.recommendedProduct` (mesma checagem já usada no `.then()` de `fetchRecommendation` hoje) e `return` imediatamente — SEM chamar `fetchRecommendation` (SC#4: zero fetch em cache hit). Se `cached` for `null` (miss), manter o fluxo atual de `fetchRecommendation(productId).then(...)`, mas adicionar `setCachedRecommendation(window.sessionStorage, productId, data, Date.now());` como a PRIMEIRA linha dentro do `.then(function (data) { ... })` (cachear o resultado da busca, mesmo quando `data.recommendedProductId` for ausente/null — evita rebuscar um "sem recomendação" a cada página vista também).

    No final da IIFE, IMEDIATAMENTE ANTES do bloco existente `if (document.readyState === 'loading') { ... } else { init(); }`, adicionar um guard: `if (typeof module !== 'undefined' && module.exports) { module.exports = { getCachedRecommendation: getCachedRecommendation, setCachedRecommendation: setCachedRecommendation }; return; }`. Em um `<script>` clássico real no navegador, `module` nunca é declarado, então `typeof module` avalia para `'undefined'` com segurança (nunca lança `ReferenceError`) e este bloco nunca executa — o comportamento em produção fica idêntico ao de hoje. Este guard existe SOMENTE para permitir que `main.test.js` importe as duas funções puras sem precisar de jsdom nem executar o restante do arquivo (que depende de `document`/`window` reais).

    Criar `storefront-script/main.test.js` (arquivo novo, primeiro teste automatizado deste script) com um helper local `createFakeStorage(initial)` que retorna um objeto `{ getItem, setItem }` apoiado num objeto JS simples (sem `Map`/classe, mesmo estilo simples do resto do projeto) — nenhuma dependência nova instalada, nenhum jsdom. Importar `getCachedRecommendation`/`setCachedRecommendation` via `import { getCachedRecommendation, setCachedRecommendation } from './main.js';` (interop CJS→ESM via `module.exports` já validado nesta fase). Cobrir os 6 comportamentos do `<behavior>` acima: hit dentro do TTL, miss após 24h+1ms, miss em storage vazio, miss/não-lança em JSON corrompido, `setCachedRecommendation` não lança quando `storage.setItem` lança, e isolamento de chave por `productId`.
