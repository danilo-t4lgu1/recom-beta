# Phase 03.1: Code Review Report

**Reviewed:** 2026-07-15T00:00:00Z
**Depth:** standard
**Files Reviewed:** 10

## Summary

Reviewed the Product Group (Grupo de Produtos, D-26 to D-35) feature end to end: schema migration, ingestion merge-by-categoryNames (D-33), the pure `product-group.js` resolver, and the extended `recommendation-engine.js` quota/backfill/cascade logic. I traced the quota-composition function (`composeGroupQuota`) against every backfill/cascade test in `recommendation-engine.test.js` (Tests 11-28) by hand and did not find a correctness defect in the core group-merge/backfill/ordering logic — the slicing bounds are non-overlapping and the "never invent a candidate" invariant (D-29) holds in every traced scenario, including double-shortfall and single-shortfall cases.

No BLOCKER-level defects were found in this pass. The findings below are all robustness/edge-case gaps and quality issues: a fragile idempotent-migration path in `catalog-store.js` that can leave the database permanently unopenable if a crash lands between two `ALTER TABLE` calls, a Unicode-normalization gap in exact-match category resolution that could silently misclassify accented category names, a determinism assumption (`Number(productId)`) that breaks silently if IDs are ever non-numeric, an unbounded pagination loop, and a couple of naming/simplification nits.

## Warnings

### WR-01: Partial-migration crash leaves catalog.db permanently unopenable

**File:** `app-partners-recomendados/src/db/catalog-store.js:38-43`
**Issue:** The idempotent migration only checks for `product_group_canonical` before running BOTH `ALTER TABLE` statements:
```js
const hasGroupColumn = catalogSnapshotColumns.some((c) => c.name === 'product_group_canonical');
if (!hasGroupColumn) {
  db.exec('ALTER TABLE catalog_snapshots ADD COLUMN category_raw TEXT');
  db.exec('ALTER TABLE catalog_snapshots ADD COLUMN product_group_canonical TEXT');
}
```
If the process is killed/crashes between the two `db.exec` calls (e.g. OOM-kill, power loss, forced termination during ingestion), `category_raw` will exist but `product_group_canonical` will not. On the next module load, `hasGroupColumn` is still `false`, so the code re-runs `ALTER TABLE catalog_snapshots ADD COLUMN category_raw TEXT`, which throws `SQLITE_ERROR: duplicate column name: category_raw`. This exception happens at **module import time** (top-level code, not inside a function callers can catch), so every future `node` process that imports `catalog-store.js` — including the CLI entry point and the test suite — will crash immediately and permanently until someone manually repairs `data/catalog.db`. There is no test covering this partial-migration state (`catalog-store.test.js` Test 2 only covers the fully-pre-migration schema).
**Fix:** Check each column independently and add only the missing one(s):
```js
const columnNames = new Set(catalogSnapshotColumns.map((c) => c.name));
if (!columnNames.has('category_raw')) {
  db.exec('ALTER TABLE catalog_snapshots ADD COLUMN category_raw TEXT');
}
if (!columnNames.has('product_group_canonical')) {
  db.exec('ALTER TABLE catalog_snapshots ADD COLUMN product_group_canonical TEXT');
}
```

### WR-02: Exact category match has no Unicode normalization — accented names can silently fail to map

**File:** `app-partners-recomendados/src/ingestion/product-group.js:80-83`
**Issue:** `resolveProductGroup` normalizes only via `trim()` + `toLowerCase()`:
```js
export function resolveProductGroup(categoryRaw) {
  if (typeof categoryRaw !== 'string') return null;
  return CATEGORY_TO_GROUP_MAP.get(categoryRaw.trim().toLowerCase()) ?? null;
}
```
`CATEGORY_TO_GROUP_MAP` keys are hardcoded in NFC form (`'calças'`, `'macacões'`). If the Nuvemshop API (or an admin who typed the category name on a different OS/input method) ever returns the same visible string in NFD form (combining diacritics, e.g. `c` + U+0327 instead of the precomposed `ç`), `Map.get` will miss even though the strings render identically and are semantically the same category. Per the module's own design note (D-26 exhaustiveness), a miss here is supposed to be "impossible" for the 11 known categories, but this specific normalization gap is exactly the kind of "grafia" variation the header comment (line ~33) flags as an expected cause of unmapped categories — it's surfaced via `console.warn` (Pitfall 3), not silent data loss, but it means legitimate, correctly-spelled categories can drop out of the recommendation engine (`productGroupCanonical: null`) due to encoding rather than an actual taxonomy problem.
**Fix:** Normalize with `.normalize('NFC')` before the map lookup (and ideally when building `CATEGORY_TO_GROUP_MAP` keys, to be defensive against either form):
```js
return CATEGORY_TO_GROUP_MAP.get(categoryRaw.trim().toLowerCase().normalize('NFC')) ?? null;
```

### WR-03: `compareByProductIdAsc` determinism guard breaks silently for non-numeric productIds

**File:** `app-partners-recomendados/src/recommendation/recommendation-engine.js:298-300`
**Issue:**
```js
function compareByProductIdAsc(a, b) {
  return Number(a.productId) - Number(b.productId);
}
```
The docstring above this function states it "garante a mesma saída independente da ordem de entrada" (guarantees the same output regardless of input order) — this is the RULE-02 determinism guard. If `productId` is ever not a clean numeric string (e.g. a UUID, or an ID with a non-numeric prefix), `Number(...)` produces `NaN` for both operands, so the comparator returns `NaN`. `Array.prototype.sort` behavior for a comparator that returns `NaN` is not guaranteed to be stable/deterministic across engines per spec, which directly undermines the guarantee this function exists to provide. Nothing today catches or logs this; it fails silently by producing whatever order the engine's internal sort happens to yield.
**Fix:** Fall back to string comparison when either ID doesn't parse cleanly, so the guard degrades to still-deterministic (if not numerically ordered) behavior instead of `NaN`:
```js
function compareByProductIdAsc(a, b) {
  const numA = Number(a.productId);
  const numB = Number(b.productId);
  if (Number.isNaN(numA) || Number.isNaN(numB)) {
    return String(a.productId).localeCompare(String(b.productId));
  }
  return numA - numB;
}
```

### WR-04: Unbounded pagination loop in `listAllProductsInCategory`

**File:** `app-partners-recomendados/src/ingestion/ingest-catalog.js:97-110`
**Issue:**
```js
async function listAllProductsInCategory(categoryId, limiter) {
  const allProducts = [];
  let page = 1;
  let hasNextPage = true;

  while (hasNextPage) {
    const result = await listProducts({ categoryId, page, perPage: 200, limiter });
    allProducts.push(...result.products);
    hasNextPage = result.hasNextPage;
    page += 1;
  }

  return allProducts;
}
```
There is no maximum page count / safety cap. If `listProducts` (or the underlying API) ever returns `hasNextPage: true` incorrectly on the last page (API bug, or an off-by-one in the Nuvemshop client), this loop never terminates, and since it runs inside `runIngestion` before `startIngestionRun` is even called, the ingestion run never gets recorded as `failed` — it just hangs indefinitely with no run row to signal something is wrong.
**Fix:** Add a sane upper bound (e.g. `MAX_PAGES = 1000`) and throw a clear error if exceeded, so a runaway loop becomes an observable failure instead of a silent hang:
```js
const MAX_PAGES = 1000;
while (hasNextPage) {
  if (page > MAX_PAGES) {
    throw new Error(`listAllProductsInCategory: excedeu ${MAX_PAGES} páginas para categoryId=${categoryId} — possível loop infinito da paginação.`);
  }
  ...
}
```

### WR-05: `recommendForProduct` never checks the source product's own `hasAvailableGrade` — untested behavior

**File:** `app-partners-recomendados/src/recommendation/recommendation-engine.js:344-388`
**Issue:** `isEligibleCandidateInGroup` checks `candidate.hasAvailableGrade` (line 141), but `recommendForProduct` itself only gates on `source.colorValue == null` (line 354) and `sourceGroup == null` (line 361) — it never checks whether the *source* product itself has an available stock grade. This means a product that is currently out of stock (`hasAvailableGrade: false`) still generates a full recommendation list. That may well be the intended behavior (recommend alternatives for an out-of-stock item), but nothing in the file's docstring or the 29-test suite confirms this was a deliberate decision — every fixture in `recommendation-engine.test.js` uses the `makeProduct` default of `hasAvailableGrade: true` for the source, so this path is entirely untested either way.
**Fix:** Either add an explicit test asserting the intended behavior (source out-of-stock still returns recommendations) to lock in the decision, or add a guard if the intended rule is that unavailable sources should return `[]`:
```js
if (!source.hasAvailableGrade) return []; // if D-15 requires source availability too
```

### WR-06: Comma-joined `categoryName`/`categoryId` in multi-category runs is lossy if a category name itself contains a comma

**File:** `app-partners-recomendados/src/ingestion/ingest-catalog.js:176-179`
**Issue:**
```js
const runId = startIngestionRun({
  categoryId: resolvedCategories.map((c) => c.id).join(','),
  categoryName: resolvedCategories.map((c) => c.name).join(', '),
});
```
Category names/ids are joined with `,`/`, ` into a single string persisted in `ingestion_runs`. If any category name itself ever contains a comma (unlikely for the current 11 known categories, but not validated anywhere), this join becomes ambiguous and unparseable by any future consumer that tries to split it back into individual category names.
**Fix:** Persist as JSON (e.g. `JSON.stringify(resolvedCategories.map((c) => c.name))`) or accept the current limitation explicitly with a code comment noting category names are assumed comma-free (matching the D-26 exhaustiveness assumption already made elsewhere in this phase).

## Info

### IN-01: Confusing variable naming in `composeGroupQuota` backfill logic

**File:** `app-partners-recomendados/src/recommendation/recommendation-engine.js:190-207`
**Issue:** `sameBackfill` is sourced **from** `crossPoolSorted` (used when the same-group side is short), and `crossBackfill` is sourced **from** `samePoolSorted` (used when the cross-group side is short). The names describe which side's *shortfall* is being filled, not where the backfilled items come from, which makes the function require careful re-reading against its own docstring to verify correctness on every future change.
**Fix:** Rename to make the data source explicit, e.g. `sameShortfallFilledFromCross` / `crossShortfallFilledFromSame`, or add inline comments at each assignment clarifying direction.

### IN-02: Redundant `Map.has`/`Map.get` pattern in `getLatestSnapshotProducts`

**File:** `app-partners-recomendados/src/db/catalog-store.js:198`
**Issue:**
```js
colorValue: firstColorByProduct.has(productId) ? firstColorByProduct.get(productId) : null,
```
This does two map lookups where one suffices, since the map never stores `undefined` as a value.
**Fix:**
```js
colorValue: firstColorByProduct.get(productId) ?? null,
```

### IN-03: `product.tags` assumed to always be a string

**File:** `app-partners-recomendados/src/ingestion/ingest-catalog.js:230`
**Issue:** `(product.tags || '').split(',')` will throw `TypeError: product.tags.split is not a function` if `product.tags` is ever a non-string truthy value (e.g., an array, which some third-party API wrappers normalize tags into). This is pre-existing behavior not introduced by this phase, but it sits directly next to the new D-32/D-26 category-extraction code added in this diff and shares the same "trust the API shape" assumption that `extractCategoryRaw` explicitly guards against with defensive optional chaining. Worth hardening for consistency.
**Fix:** `(typeof product.tags === 'string' ? product.tags : '').split(',')`.
