### `src/ingestion/product-group.js` (NEW — utility, transform)

**Analog:** `src/ingestion/fabric-taxonomy.js` (`resolveFabricTagFromTags`, lines 37-69) — the D-32 keyword-containment resolver is the direct precedent named in the task brief; this is a same-day sibling problem (category→group vs. tag→fabric).

**Header comment pattern** (lines 1-36 of analog): a long top-of-file comment block documenting the decision ID (D-06→D-32 there; D-26→D-31 here), why the approach was chosen (substring-containment, NOT fuzzy matching — explicitly banned per Pitfall 6/T-02-07), and what NEVER to do. Copy this structure, referencing D-26/D-32(precedent)/Pitfall 3 instead.

**Core resolver pattern** (lines 37-69 — copy structure exactly, swap fabric keywords for category names and drop the substring-containment mechanic since category names are exact enum values, not composite strings):
```javascript
const FABRIC_KEYWORD_TO_CANONICAL = new Map([
  ['bengaline', 'malha'],
  ['malha', 'malha'],
  ['crepe', 'crepe'],
  // ...
]);

export function resolveFabricTagFromTags(rawTags) {
  const tags = Array.isArray(rawTags) ? rawTags : [];
  for (const tag of tags) {
    if (typeof tag !== 'string') continue;
    const normalized = tag.trim().toLowerCase();
    for (const [keyword, canonical] of FABRIC_KEYWORD_TO_CANONICAL) {
      if (normalized.includes(keyword)) {
        return { fabricTagRaw: tag.trim(), fabricTagCanonical: canonical };
      }
    }
  }
  return { fabricTagRaw: null, fabricTagCanonical: null };
}
```

For `resolveProductGroup`, RESEARCH.md already gives the exact target shape (copy verbatim, it already follows this analog's conventions):
```javascript
export const GROUP_LOOK_INTEIRO = 'Look Inteiro';
export const GROUP_PARTES_DE_CIMA = 'Partes de Cima';
export const GROUP_PARTES_DE_BAIXO = 'Partes de Baixo';

const CATEGORY_TO_GROUP_MAP = new Map([
  ['vestidos', GROUP_LOOK_INTEIRO],
  ['macacoes', GROUP_LOOK_INTEIRO],
  ['macaquinhos', GROUP_LOOK_INTEIRO],
  ['blusas', GROUP_PARTES_DE_CIMA],
  ['croppeds', GROUP_PARTES_DE_CIMA],
  ['corsets', GROUP_PARTES_DE_CIMA],
  ['camisas e coletes', GROUP_PARTES_DE_CIMA],
  ['blazers e jaquetas', GROUP_PARTES_DE_CIMA],
  ['calcas', GROUP_PARTES_DE_BAIXO],
  ['shorts', GROUP_PARTES_DE_BAIXO],
  ['saias', GROUP_PARTES_DE_BAIXO],
]);

export function resolveProductGroup(categoryRaw) {
  if (typeof categoryRaw !== 'string') return null;
  return CATEGORY_TO_GROUP_MAP.get(categoryRaw.trim().toLowerCase()) ?? null;
}

export function crossGroupOf(group) {
  if (group === GROUP_PARTES_DE_CIMA) return GROUP_PARTES_DE_BAIXO;
  if (group === GROUP_PARTES_DE_BAIXO) return GROUP_PARTES_DE_CIMA;
  return null;
}
```

**Key divergence from the fabric analog to note explicitly in the new file's header comment:** fabric resolution uses substring-containment because tags are composite free text (D-32); category resolution should use **exact match after normalize (trim+lowercase)** because category names are a closed, single-value-per-product enum (D-26) — do not copy the substring `.includes()` loop mechanic, only the Map-based dispatch structure and the "never throws, returns null for unknown" contract.

**Unmapped-category auditing (Pitfall 3):** unlike fabric (`auditFabricTags`, unmapped = expected/benign), unmapped category is unexpected and must be logged/audited visibly. Analog for the audit-table mechanism: `auditFabricTags` (lines 80-98 of `fabric-taxonomy.js`) + `fabric_tag_audit` table (see schema.sql section below) + `insertFabricAudit`/`fabricAudits` wiring in `ingest-catalog.js` (lines 229-236, 234). Replicate the same three-part shape (resolver function + audit function + audit table) for category, OR at minimum a `console.warn` per Pitfall 3's "how to avoid" — planner's discretion per RESEARCH.md, but the audit-table shape already exists to copy if chosen.

```javascript
function isEligibleCandidate(source, candidate) {
  if (!candidate) return false;
  if (String(candidate.productId) === String(source.productId)) return false;
  if (!candidate.hasAvailableGrade) return false;
  if (candidate.fabricTagCanonical == null) return false;
  if (candidate.colorValue == null) return false;

  const sameColor = normalizeMatchValue(candidate.colorValue) === normalizeMatchValue(source.colorValue);
  const sameFabric = normalizeMatchValue(candidate.fabricTagCanonical) === normalizeMatchValue(source.fabricTagCanonical);

  return sameColor && sameFabric;
}
```

## Shared Patterns

### Zero-I/O / zero-import purity (RULE-02)
**Source:** `src/recommendation/recommendation-engine.js` header comment (lines 1-8) and `src/ingestion/fabric-taxonomy.js` header comment (lines 1-33).
**Apply to:** `recommendation-engine.js` modifications, and any new `product-group.js` usage FROM the engine (must be inlined/duplicated, not imported, if consumed by the engine — group resolution should instead happen at ingestion time per RESEARCH.md's Pattern 1 recommendation, so the engine only ever sees the already-resolved `productGroupCanonical` field, never raw category names).

### Never-throw / null-on-unknown contract
**Source:** `resolveFabricTagFromTags` (fabric-taxonomy.js lines 57-69), `isEligibleCandidate`/`recommendForProduct` (recommendation-engine.js, e.g. lines 236 `if (!source) return []`).
**Apply to:** `resolveProductGroup` (unknown category → `null`, never throw), and all engine extensions (malformed input → `[]`, never throw — same convention T-02-06).

### Prepared statements with named params (T-02-04, SQL injection mitigation)
**Source:** every `db.prepare(...).run(params)` call in `catalog-store.js` (e.g. lines 45-51, 53-56).
**Apply to:** the extended `insertSnapshot` statement and any new `insertCategoryAudit` statement — never string-concatenate `categoryRaw` (external API data) into SQL.

### Decision-ID-annotated header/inline comments
**Source:** every file read (`fabric-taxonomy.js`, `recommendation-engine.js`, `ingest-catalog.js`, `catalog-store.js`, `schema.sql`) consistently cites decision IDs (D-06, D-13, D-32, T-02-04, etc.) directly in comments next to the code they justify.
**Apply to:** all new/modified files this phase — cite D-26 through D-35 inline at the exact lines implementing each decision, matching this codebase's established documentation discipline.

### Test fixture builder + `describe`/`it (Test N)` convention
**Source:** `recommendation-engine.test.js` lines 14-37 (`makeVariant`/`makeProduct` factories), `fabric-taxonomy.test.js` lines 12-21 (plain inline fixtures, simpler domain).
**Apply to:** `recommendation-engine.test.js` new cases (extend `makeProduct`) and new `product-group.test.js` (plain fixtures, following the simpler `fabric-taxonomy.test.js` style since `resolveProductGroup` takes a scalar string, not an array).
