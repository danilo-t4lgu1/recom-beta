- **D-31:** D-26 a D-30 **não reabrem** D-14 (Fase 3) — "Grupo" aqui é estrutural (pool elegível e cota), não um nível extra da cascata de desempate por estoque. D-14 permanece válida (cascata de desempate é só estoque, 3 níveis).

## Summary

Esta fase estende `recommendation-engine.js` (módulo puro, zero imports, já testado com 16 casos verdes) para incorporar uma quarta dimensão de elegibilidade — Grupo de Produtos — que hoje **não existe em nenhum lugar do schema persistido**: `schema.sql` só grava `category_id`/`category_name` em `ingestion_runs` (metadado do RUN, não do produto). Confirmei por leitura direta do código que a API pública da Nuvemshop (`GET /products`) já devolve, por produto, um campo `categories[]` — array de objetos completos (`id`, `name.{es,en,pt}`, `handle`, `parent`, `subcategories`) — mas `ingest-catalog.js`/`client.js` simplesmente descartam esse campo hoje; não é preciso nenhuma chamada nova à API, só extrair um campo que já chega na resposta atual de `listProducts()`.

A decisão de maior impacto no design é **onde vive o mapeamento categoria→grupo**. Ao contrário do padrão de tecido (`fabric_tag_canonical_map`, uma tabela de dados, porque as tags são texto livre curado manualmente e mudam), aqui o conjunto de categorias é um enum pequeno e fechado (11 nomes conhecidos, confirmados pelo usuário como exaustivos — "a loja não trabalha com categorias fora desses 3 grupos"), controlado pelo admin da Nuvemshop, não por texto livre. **Recomendação: constante em código** (`CATEGORY_TO_GROUP_MAP`), não uma tabela nova — ver justificativa completa em `## Architecture Patterns`.

A restruturação de `isEligibleCandidate`/`recommendForProduct` é decomponível em funções puras pequenas (mesmo padrão RULE-02 já em vigor): resolver o grupo do produto-fonte, montar dois pools (mesmo grupo com critério completo, grupo cruzado com critério reduzido) quando o grupo mesclável se aplica, e compor a cota 4+4 com backfill simétrico como uma função separada e testável isoladamente.

**Achado não-antecipado pelo CONTEXT.md (Pitfall 1, alta relevância para o planejamento):** a arquitetura atual de ingestão/leitura (`runIngestion` por categoria única + `getLatestSnapshotProducts()` lendo só o **run_id mais recente**) não suporta múltiplas categorias simultaneamente em um snapshot de trabalho. Isso não é um problema de "ingerir dados reais é só operação" como o `CONTEXT.md` assumiu — é uma limitação estrutural que vai bloquear qualquer teste end-to-end contra `catalog.db` real assim que houver mais de uma categoria ingerida, e continuará bloqueando a Fase 4/5/6 em produção (quando o catálogo completo precisar ser lido de uma vez). O planejador precisa decidir explicitamente se resolve isso nesta fase ou a documenta como débito técnico consciente.

**Primary recommendation:** adicionar `categoryRaw`/`productGroupCanonical` em `catalog_snapshots` (seguindo o padrão fabric), resolver o grupo via constante de código (não tabela), decompor o motor em `resolveGroup` → `buildEligiblePool` (parametrizado por critério completo/reduzido) → `composeGroupQuota` (4+4 + backfill) → `recommendForProduct` (orquestrador), e tratar a limitação de ingestão multi-categoria como uma decisão explícita de escopo (task nova ou débito documentado), não como um não-problema.

### Pattern 1: Constante de mapeamento categoria→grupo (em vez de tabela)

**What:** um objeto/`Map` JS estático no topo de `recommendation-engine.js` (ou um módulo irmão dedicado, ex. `product-group.js`, se o motor precisar continuar com zero imports — ver nota de pureza abaixo) que mapeia os 11 nomes de categoria conhecidos para um dos 3 grupos canônicos.
**When to use:** resolução de grupo tanto na ingestão (grava `productGroupCanonical` já resolvido) quanto, se necessário, em qualquer leitura futura.
**Nota de pureza (RULE-02):** se este mapeamento for usado pelo MOTOR diretamente (não só na ingestão), ele deve ser uma constante DENTRO do próprio arquivo do motor (ou duplicada/importada só de um módulo igualmente puro, sem I/O) — nunca lido de uma tabela em tempo de execução do motor, isso quebraria a garantia de zero I/O que a Fase 3 já validou (Test 10, stub de fetch nunca invocado). Recomendação concreta: resolver o grupo **na ingestão**, gravar `productGroupCanonical` já resolvido em `catalog_snapshots`, e o motor **nunca vê nomes de categoria crus** — só o valor canônico já resolvido, exatamente como já acontece hoje com `fabricTagCanonical` (o motor não conhece a tabela `fabric_tag_canonical_map`, só consome o valor já resolvido pela ingestão).

```javascript
// Sugestão de nome/local: src/ingestion/product-group.js (módulo puro, mesmo
// padrão de fabric-taxonomy.js — testável isoladamente, sem I/O)

export const GROUP_LOOK_INTEIRO = 'Look Inteiro';
export const GROUP_PARTES_DE_CIMA = 'Partes de Cima';
export const GROUP_PARTES_DE_BAIXO = 'Partes de Baixo';

// D-26: mapeamento fechado, confirmado pelo usuário como exaustivo no catálogo real.
const CATEGORY_TO_GROUP_MAP = new Map([
  ['vestidos', GROUP_LOOK_INTEIRO],
  ['macacoes', GROUP_LOOK_INTEIRO],
  ['macaquinhos', GROUP_LOOK_INTEIRO],
  ['blusas', GROUP_PARTES_DE_CIMA],
  ['croppeds', GROUP_PARTES_DE_CIMA],
  ['corsets', GROUP_PARTES_DE_CIMA],
  ['camisas e coletes', GROUP_PARTES_DE_CIMA],
  ['blazers e jaquetas', GROUP_PARTES_DE_CIMA],
  ['calcas', GROUP_PARTES_DE_BAIXO],
  ['shorts', GROUP_PARTES_DE_BAIXO],
  ['saias', GROUP_PARTES_DE_BAIXO],
]);

// resolveProductGroup: normaliza (trim+lowercase, mesma convenção de
// normalizeMatchValue em recommendation-engine.js) e resolve. Categoria
// desconhecida -> null (produto fica fora do motor, mesma postura de D-09/D-15
// para tecido não mapeado — NÃO lança erro), mas deve ser logada/auditada
// (ver Pitfall 3) porque, ao contrário de tecido, categoria desconhecida aqui
// é sinal de dado inesperado, não de "planilha ainda não importada".
export function resolveProductGroup(categoryRaw) {
  if (typeof categoryRaw !== 'string') return null;
  return CATEGORY_TO_GROUP_MAP.get(categoryRaw.trim().toLowerCase()) ?? null;
}

// D-27/D-28: qual grupo mescla com qual. Look Inteiro não tem par (auto-contido).
export function crossGroupOf(group) {
  if (group === GROUP_PARTES_DE_CIMA) return GROUP_PARTES_DE_BAIXO;
  if (group === GROUP_PARTES_DE_BAIXO) return GROUP_PARTES_DE_CIMA;
  return null; // Look Inteiro, ou grupo desconhecido
}
```

### Pattern 2: Decomposição de `recommendForProduct` (pools + cota + backfill)

**What:** extensão do motor mantendo `isEligibleCandidate`/`buildRecommendation`/`compareRecommendations` como estão (D-13/D-15/D-27 inalterados), adicionando uma camada de composição de pools acima deles.
**When to use:** sempre que o produto-fonte for de um grupo mesclável (Partes de Cima/Baixo); Look Inteiro usa o caminho antigo, sem alteração.

```javascript
// Extensão de isEligibleCandidate: parametrizado por "requireFabric" para
// suportar o critério reduzido do grupo cruzado (D-28), sem duplicar a lógica
// de cor/estoque/auto-exclusão.
function isEligibleCandidateInGroup(source, candidate, targetGroup, { requireFabric }) {
  if (!candidate) return false;
  if (String(candidate.productId) === String(source.productId)) return false;
  if (!candidate.hasAvailableGrade) return false;
  if (candidate.colorValue == null) return false;
  if (candidate.productGroupCanonical !== targetGroup) return false;

  if (requireFabric) {
    if (candidate.fabricTagCanonical == null) return false;
    const sameFabric =
      normalizeMatchValue(candidate.fabricTagCanonical) ===
      normalizeMatchValue(source.fabricTagCanonical);
    if (!sameFabric) return false;
  }
  // requireFabric === false (D-28, bloco cruzado): tecido NÃO é considerado,
  // nem como filtro nem como exigência de não-nulo — candidato com fabric null
  // passa normalmente aqui.

  return normalizeMatchValue(candidate.colorValue) === normalizeMatchValue(source.colorValue);
}

function buildSortedPool(source, catalog, targetGroup, { requireFabric }) {
  return catalog
    .filter((c) => isEligibleCandidateInGroup(source, c, targetGroup, { requireFabric }))
    .map(buildRecommendation)
    .sort(compareRecommendations); // D-13 cascata, inalterada
}

// D-29: cota 4+4 com backfill simétrico. Pura, testável isoladamente com
// arrays já ordenados (sem precisar de catálogo/produto real).
function composeGroupQuota(samePoolSorted, crossPoolSorted, { quota = 4, cap = 8 } = {}) {
  const same = samePoolSorted.slice(0, quota);
  const cross = crossPoolSorted.slice(0, quota);

  const sameShortfall = quota - same.length;
  const crossShortfall = quota - cross.length;

  // Backfill do lado cruzado usando o RESTANTE do pool mesmo-grupo (já ordenado,
  // continuando a partir da posição `quota`), respeitando o critério do
  // mesmo-grupo (requireFabric: true) — D-29.
  const crossBackfill = crossShortfall > 0
    ? samePoolSorted.slice(quota, quota + crossShortfall)
    : [];

  // Backfill do lado mesmo-grupo usando o restante do pool cruzado — D-29.
  const sameBackfill = sameShortfall > 0
    ? crossPoolSorted.slice(quota, quota + sameShortfall)
    : [];

  return [...same, ...sameBackfill, ...cross, ...crossBackfill].slice(0, cap);
}
```

**Ordem final do array retornado (ponto em aberto, ver `## Open Questions`):** o pseudocódigo acima concatena "bloco mesmo-grupo (+ seu backfill)" antes de "bloco cruzado (+ seu backfill)". O `CONTEXT.md` não especifica a ordem final entre os dois blocos — só que cada bloco é ordenado internamente pela cascata D-13. Esta é uma escolha razoável e determinística, mas é discricionária; o planejador deve confirmar ou ajustar.

```javascript
// Orquestrador final — substitui apenas o corpo de recommendForProduct,
// mantendo a mesma assinatura pública (compatibilidade com Fase 4/D-20).
export function recommendForProduct(productId, catalogProducts, options = {}) {
  const catalog = Array.isArray(catalogProducts) ? catalogProducts : [];
  const targetId = String(productId);
  const source = catalog.find((p) => p && String(p.productId) === targetId);

  if (!source) return [];
  if (source.fabricTagCanonical == null || source.colorValue == null) return [];

  const sourceGroup = source.productGroupCanonical;
  const crossGroup = crossGroupOf(sourceGroup);

  if (!crossGroup) {
    // Look Inteiro (D-27) ou grupo desconhecido: caminho original, inalterado.
    return catalog
      .filter((c) => isEligibleCandidate(source, c)) // função original, sem grupo
      .map(buildRecommendation)
      .sort(compareRecommendations)
      .slice(0, options.maxRecommendations ?? MAX_RECOMMENDATIONS);
  }

  const samePool = buildSortedPool(source, catalog, sourceGroup, { requireFabric: true });
  const crossPool = buildSortedPool(source, catalog, crossGroup, { requireFabric: false });

  return composeGroupQuota(samePool, crossPool, {
    quota: 4,
    cap: options.maxRecommendations ?? MAX_RECOMMENDATIONS,
  });
}
```

**Nota importante — caminho "Look Inteiro" acima reaproveita `isEligibleCandidate` original SEM checar grupo.** Isso é intencional e seguro apenas porque D-26 confirma que hoje não existe produto multi-grupo; mas para ficar 100% correto por construção (não só "correto porque os dados de hoje cooperam"), o caminho Look Inteiro **deveria também filtrar por `candidate.productGroupCanonical === GROUP_LOOK_INTEIRO`** — do contrário, um candidato de Partes de Cima com mesma cor+tecido+estoque de um Vestido-fonte seria elegível por engano caso a extensão de fabric/cor coincida entre grupos diferentes no catálogo real futuro. Recomendação: adicionar esse filtro de grupo também no caminho Look Inteiro, não confiar apenas na ausência histórica de dado multi-grupo. Isso é uma correção de robustez sobre o pseudocódigo acima, não uma mudança de regra de negócio (D-27 já diz "só recomendam entre si").

### Anti-Patterns to Avoid

- **Resolver `productGroupCanonical` dentro do motor lendo uma tabela em tempo de execução:** quebra a garantia de zero I/O (RULE-02, Test 10 já existente). Resolver sempre na ingestão, motor só consome o valor já resolvido.
- **Adicionar "Grupo" como 4º nível da cascata de desempate D-13:** já descartado explicitamente por D-14/D-30/D-31 — grupo decide o POOL, nunca a ORDEM dentro de um pool já formado.
- **Reimplementar `isEligibleCandidate` do zero em vez de parametrizar:** duplicaria a lógica de cor/auto-exclusão/estoque já testada — usar composição (`requireFabric` como parâmetro) preserva os 16 testes existentes intactos.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Normalização de nome de categoria para lookup | Nova função de normalização | `normalizeMatchValue`-like (trim+lowercase), já existe convenção idêntica no arquivo | Consistência com o resto do motor; qualquer divergência de normalização entre cor/tecido/categoria é uma fonte clássica de bug silencioso |
| Ordenação dentro de cada pool (mesmo-grupo/cruzado) | Um novo comparador "por grupo" | `compareRecommendations` já existente (D-13), reaplicado a cada pool | D-30 é explícito: a cascata não muda, só o pool de entrada muda |

**Key insight:** esta fase é, estruturalmente, "adicionar um filtro de pool antes da cascata existente" — não "adicionar um critério novo à cascata". ## Common Pitfalls

### Pitfall 1: Arquitetura de ingestão/leitura não suporta múltiplas categorias num único snapshot de trabalho (achado novo, não estava no CONTEXT.md)

**What goes wrong:** `runIngestion({ categoryName })` sempre resolve **uma única categoria por chamada** e grava seus produtos sob um novo `run_id`. `getLatestSnapshotProducts()` lê **apenas o `run_id` mais recente com status `success`** (`selectLatestSuccessfulRun`) e filtra tanto `catalog_snapshots` quanto `variants` (via `last_seen_run_id`) por esse único `run_id`. Se você rodar `runIngestion({categoryName: 'Vestidos'})` e depois `runIngestion({categoryName: 'Blusas'})`, o segundo run se torna "o mais recente" e `getLatestSnapshotProducts()` passa a devolver **só os produtos de Blusas** — os produtos de Vestidos (embora ainda existam nas tabelas `products`/`variants` via upsert) ficam com `last_seen_run_id` do run ANTERIOR e desaparecem do snapshot de trabalho.
**Why it happens:** o design de Fase 2 foi otimizado para "1 categoria piloto por vez" (D-01: Vestidos como piloto) — nunca precisou combinar categorias porque só havia uma. Esta fase é a primeira a exigir explicitamente múltiplas categorias vivas simultaneamente no mesmo snapshot (para a mescla Partes de Cima ↔ Baixo funcionar de verdade).
**How to avoid:** decisão de escopo explícita e necessária para o planejador — não é "operação, não código" como o `CONTEXT.md` assumiu. Duas rotas concretas: (a) estender `runIngestion` para aceitar múltiplas `categoryName[]` e persistir todas sob o MESMO `run_id`; ou (b) redesenhar `getLatestSnapshotProducts()` para agregar o último run bem-sucedido **por categoria distinta** (não o último run global) e unir os resultados. (a) é mais simples de implementar e mais alinhado ao padrão "1 transação por execução de ingestão" já em uso; (b) evita re-ingerir categorias que não mudaram a cada execução. Qualquer uma resolve o bloqueio; nenhuma decisão aqui é travada pelo `CONTEXT.md` — precisa ir para o plano.
**Warning signs:** um teste ou script manual que ingere 2 categorias sequencialmente e depois lê `getLatestSnapshotProducts()` esperando ver ambas, mas só vê a última.

### Pitfall 2: Migração de coluna silenciosamente ignorada por `CREATE TABLE IF NOT EXISTS`

**What goes wrong:** adicionar `category_raw`/`product_group_canonical` ao `CREATE TABLE catalog_snapshots` em `schema.sql` não tem efeito nenhum em bancos `data/catalog.db` já existentes no disco (dev ou produção futura) — a tabela já existe, `IF NOT EXISTS` pula a criação inteira, inclusive das novas colunas.
**Why it happens:** é o mesmo padrão que já funcionou para toda a Fase 2/3 (schema nunca mudou depois de criado) — esta é a primeira vez que o schema precisa evoluir sobre uma tabela já populada.
**How to avoid:** adicionar um passo de migração idempotente em `catalog-store.js` (checagem via `PRAGMA table_info` ou `ALTER TABLE ... ADD COLUMN` com captura de erro "duplicate column name") executado toda vez que o módulo inicializa, antes ou depois de `db.exec(schema.sql)`.
**Warning signs:** `INSERT INTO catalog_snapshots (..., category_raw, product_group_canonical) VALUES (...)` lançando `SQLITE_ERROR: table catalog_snapshots has no column named category_raw` ao rodar contra um `catalog.db` pré-existente (vai acontecer de cara no ambiente de desenvolvimento atual, que já tem 3 runs gravados).

### Pitfall 3: Categoria não mapeada tratada como "silenciosamente fora do motor" sem sinalização, ao contrário do precedente de tecido

**What goes wrong:** seguir o precedente de `fabric_tag_canonical` (D-09: tag não mapeada = fora do motor, nunca erro, nunca relatório) ao pé da letra para categoria pode esconder um bug real. Tecido não-mapeado é ESPERADO (planilha ainda não importada, D-06). Categoria não-mapeada é INESPERADA (D-26 confirma que as 11 categorias conhecidas são exaustivas hoje) — se aparecer uma categoria fora do mapa, é sinal de: nome de categoria com variação de grafia, categoria nova criada no admin, ou erro de extração do campo `categories[]`.
**Why it happens:** copiar o padrão fabric sem diferenciar a semântica ("ausência esperada" vs. "ausência = bug provável").
**How to avoid:** manter o comportamento não-bloqueante (produto sem grupo mapeado fica fora do motor, nunca lança) MAS logar/auditar toda ocorrência de categoria não mapeada de forma visível (ex: `console.warn` na ingestão, ou uma tabela de auditoria leve análoga a `fabric_tag_audit`) — para que o time perceba rapidamente se uma categoria nova aparecer, em vez de produtos silenciosamente saírem do motor sem ninguém notar.
**Warning signs:** produto sumindo de todas as recomendações sem nenhuma mensagem de log explicando por quê.

### Pitfall 4: Gate de elegibilidade da fonte (`source.fabricTagCanonical == null`) pode zerar TODAS as recomendações de Partes de Cima/Baixo hoje, igual já acontece com Look Inteiro

**What goes wrong:** a checagem de entrada em `recommendForProduct` (linha 237 do código atual) já retorna `[]` se a fonte não tiver `fabricTagCanonical`. Hoje, 0/645 produtos reais têm tecido preenchido (D-16, `03-CONTEXT.md`). Se essa checagem de nível superior for mantida (recomendado, ver `## Open Questions`), então mesmo depois de implementar a mescla de grupo, **nenhum produto real de nenhum grupo vai gerar recomendações** até a planilha de tecido ser importada — inclusive para o bloco cruzado, que teoricamente não precisaria de tecido.
**Why it happens:** o gate de elegibilidade da fonte, historicamente, era "sem tecido = fora do motor completamente" (D-15), uma decisão de nível de produto, não de nível de bloco de cota.
**How to avoid:** não é um bug a corrigir — é uma implicação a comunicar claramente no plano/verificação, para não ser confundido com "a mescla de grupo não está funcionando" quando na verdade é a mesma limitação de dados já conhecida (D-16) se propagando. Os testes automatizados desta fase devem usar fixtures com `fabricTagCanonical` preenchido (mesma convenção já usada em `recommendation-engine.test.js`), não o dump real.
**Warning signs:** verificação manual contra `catalog.db` real retornando `[]` para tudo e sendo mal-interpretada como regressão da Fase 03.1.

## Open Questions

1. **Uma fonte sem `fabricTagCanonical` deveria gerar recomendações cruzadas (cor+estoque) mesmo que não gere recomendações mesmo-grupo?**
   - What we know: D-15 (Fase 3) trava que produto sem tecido fica fora do motor "nem como fonte, nem como candidato elegível" — mas essa decisão foi tomada ANTES de existir o conceito de bloco cruzado sem exigência de tecido.
   - What's unclear: se D-15 pretendia dizer "fora do motor completamente" ou "fora de qualquer match que dependa de tecido" (o que hoje é só o próprio D-15, mas passa a ser só o bloco mesmo-grupo depois desta fase).
   - Recommendation: manter o gate de nível superior como está (mais seguro, menos surpresa, consistente com a redação literal de D-15) a menos que o usuário confirme explicitamente o contrário — ver Assumption A1.

2. **Como resolver a limitação de múltiplas categorias em um único snapshot de trabalho (Pitfall 1)?**
   - What we know: bloqueia testes end-to-end reais contra `catalog.db` com mais de uma categoria; fixtures sintéticas cobrem os testes automatizados sem depender disso.
   - What's unclear: se o planejador trata isso como task desta fase (estender `runIngestion`/`getLatestSnapshotProducts`) ou como débito técnico documentado para depois — mas precisa ser uma decisão CONSCIENTE, não assumida como "só rodar o comando" (correção da premissa do `CONTEXT.md`).
   - Recommendation: pelo menos documentar explicitamente a limitação no plano (mesmo que a correção fique fora do escopo desta fase), porque ela vai bloquear qualquer validação real da mescla de grupo assim que o usuário terminar de popular tags de tecido e quiser rodar ingestão de Blusas/Calças de verdade.

3. **Ordem final do array de retorno quando o bloco cruzado entra em jogo (Assumption A4).**
   - Recommendation: confirmar com o usuário/planejador se "mesmo-grupo primeiro" é aceitável, ou se alguma outra ordem é esperada pela Fase 4 (preview).
