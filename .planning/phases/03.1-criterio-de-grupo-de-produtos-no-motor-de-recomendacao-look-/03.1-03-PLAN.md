<objective>
Estender a camada de persistência do catálogo (`schema.sql` + `catalog-store.js`) para gravar e ler `category_raw`/`product_group_canonical` por produto (D-26), resolvendo a lacuna confirmada em `03.1-CONTEXT.md`: hoje NENHUM campo por-produto guarda a categoria/grupo — só `ingestion_runs` sabe qual categoria foi lida em cada RUN.

Endereça diretamente o Pitfall 2 do `03.1-RESEARCH.md`: `CREATE TABLE IF NOT EXISTS` é NO-OP contra um `data/catalog.db` já existente no disco (3 runs reais já gravados, confirmado em STATE.md) — adicionar as colunas ao `CREATE TABLE` de `schema.sql` sozinho NÃO as adiciona retroativamente. Este plano adiciona uma migração idempotente em `catalog-store.js` (`PRAGMA table_info` + `ALTER TABLE ... ADD COLUMN`), executada toda vez que o módulo abre o banco — mesma disciplina de idempotência já usada pelo resto do arquivo.

Para tornar essa migração genuinamente testável (nenhum teste automatizado existe hoje para `catalog-store.js` — Wave 0 gap confirmado no `03.1-VALIDATION.md`), este plano introduz um pequeno seam de testabilidade: o diretório do banco passa a ser sobrescrevível via `CATALOG_DB_DIR` (variável de ambiente), permitindo que os testes apontem para um diretório SQLite temporário e isolado, nunca tocando o `data/catalog.db` real de desenvolvimento. Comportamento em uso normal (variável ausente) é idêntico ao atual.

Purpose: sem esta camada, `productGroupCanonical` não tem onde viver entre a ingestão (Plano 03.1-04) e o motor (Plano 03.1-02) — é o elo de dados que fecha o ciclo.
Output: `schema.sql` + `catalog-store.js` estendidos + `catalog-store.test.js` novo, cobrindo migração idempotente, persistência e leitura.
</objective>
